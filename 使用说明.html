体积是怎么从 44 MB 降到 14.91 MB 的

debug 包把 4 种 CPU 架构（arm64 / armv7 / x86 / x86_64）的 OCR 原生库全打进去了，而手机只需要其中一种。 在 app/build.gradle 里加了 ndk { abiFilters 'arm64-v8a' }，再改打 release 包，体积直接掉三分之二。 2018 年以后的安卓机基本都是 arm64；万一遇到真装不上的老 32 位机，把那行注释掉重打一个全架构包就行。

八、识屏答题引擎（v1.2 新增）

主界面第二个按钮「识屏答题引擎」进算法实验台。不插手机也能玩：粘贴题目文本或点内置示例， 就能看到四个策略各自给每个选项打了多少分、加权融合后选了谁、置信度多少。点「截屏答题」走完整实时链路。

策略权重它在干什么
词典直查0.45题干单词 → 词库释义 → 与选项比字面重合（Jaccard），有包含关系给 0.85 保底
选项反查0.25题干是中文时，把每个选项当单词查词库，谁的释义最贴近题干谁就是答案
词形模糊0.20先做词形还原（复数/时态/比较级/副词）再查词库，抗屈折变化和 OCR 错字
离群排除0.10不看词库，只算每个选项与其余选项的"合群程度"，是排除法的量化版

融合方式：final[i] = Σ(策略分 × 权重) / Σ权重； 置信度 = 0.6×最高分 + 0.4×(最高分−第二高分)。 安全阀：四个策略都没在词库里找到实证时（多半是 OCR 把单词认错了），置信度直接打对折， 让它跨不过自动作答的 0.35 门槛 —— 宁可不答，也不乱点。

离线仿真评测（不需要安卓机）

把 Java 侧算法用 Python 原样复刻，直接读真词库造四选一题跑统计：

python tools/sim_check.py 400 11 hard 0.3 short
#        题数 种子 模式   OCR出错率 选项取单义项
场景总体准确率敢答的部分答错放弃
OCR 正常（400 题）98.2%99.0%43
OCR 30% 出错（400 题）66.5%99.3%2132

加安全阀之前：OCR 出错的 131 题里敢答 40 道、只对 17 道（等于乱猜）。
加安全阀之后：那 131 题里只敢答 2 道且全对，答错总数从 27 降到 2。
结论：瓶颈不在算法，在 OCR 准不准。想提高覆盖率，优先优化截屏清晰度（别缩太狠、按题目区域裁剪）， 而不是去堆更多匹配策略。

自动作答（可选，默认完全关闭）

三重门槛，缺一不可，所以不动它的话它就是个摆设：

  1. 系统设置 → 无障碍 → 手动打开「词拍」（必须你自己开）；
  2. 实验台里的「总开关」，默认关；
  3. 目标 App 包名白名单，默认为空 —— 不填任何界面都不会被点。

它用的是系统无障碍读屏接口（跟读屏软件、UI 自动化测试同一套）， 拿的是屏幕文字，不注入、不 hook、不改内存。
别开在有真人对战的模式里：对面是真人，机器抢答会毁掉对方体验，也违反平台规则会封号。 用在自己的练习、题库、自学内容上是另一回事。

九、已知限制与不确定点

  • 不确定：ML Kit 拉丁识别器首次调用有一次性模型加载（约几百 ms），之后常驻内存；这一步的实测值机型差异大，需要你在真机上量。
  • 不确定：OriginOS 对 MediaProjection 弹窗的复现策略（是否需要每次授权），vivo 机型表现可能与其他厂商不同。
  • 带 FLAG_SECURE 的界面截图全黑，无解。
  • 本应用不接入无障碍点击，也不具备在任何对战/考试中作答的能力 —— 这是设计上的取舍，不是技术做不到。
